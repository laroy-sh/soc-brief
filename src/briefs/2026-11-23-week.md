## What changed

Integrated Security Operations in Microsoft Defender is the week's biggest operational change, and from 17 November existing Microsoft Sentinel customers with Microsoft 365 E5, Microsoft 365 E7 or a Defender Suite licence can opt in. Core ISOC capabilities went generally available — case management, playbooks, workbooks and UEBA, plus workspace creation and third-party ingestion — while the preview expands to the full breadth of SIEM capabilities and adds SOC optimization recommendations, Content Hub, detections as code and automation audit logs, per [Ignite 2026: What's new in Microsoft Defender & Sentinel](https://techcommunity.microsoft.com/t5/microsoft-defender-blog/ignite-2026-what-s-new-in-microsoft-defender-sentinel/ba-p/4569975). Eligible customers get 90 days of built-in Defender data retention up from 30, ingestion priced at 2.4 US dollars per GB across more than 500 connectors, and a data lake for historical hunting and compliance. Opting in is optional and you can stay on Sentinel as it is today. If you do move, budget time for the portal navigation reshuffle documented on the Defender XDR what's-new page: Hunting becomes Investigation and response, Workbooks moves to Dashboards and reports, Analytics moves under Investigation and response, Automation becomes a top-level item, and every runbook or training deck that names a Microsoft Sentinel menu path will need editing. ([Ignite 2026: What's new in Microsoft Sentinel](https://techcommunity.microsoft.com/t5/microsoft-sentinel-blog/ignite-2026-what-s-new-in-microsoft-sentinel/ba-p/4571174))

Vulnerability shielding in Microsoft Defender is in preview, it is on by default, and that combination makes it the announcement to read properly rather than skim. It applies temporary hardening — reducing network reachability, restricting access paths, tightening permissions — to vulnerable systems in the gap between exposure and patch, and it works two ways. Proactively, the Risk Reduction Agent in Microsoft Perception proposes a shielding plan through the Reduce exposure risk playbook and implements nothing without your approval, simulating each plan against 90 days of real activity first. During an active attack, attack disruption applies shields autonomously, with no approval step, which is the part worth socialising with your network and application owners before it fires. Microsoft's framing of why it exists is the useful statistic: 38 percent of critical Patch Tuesday exposures remain unpatched for more than five days, and server-side remote code execution accounts for 37 percent of what adversaries exploit, which is the class the preview covers. Shields are listed with the vulnerability and devices they cover, retire automatically once the patch lands, roll back in one click, and exclusions are managed through Microsoft Intune — set those exclusions for anything that must never be touched before the feature reaches your tenant, not after. ([Vulnerability shielding: Protect the time before the patch](https://techcommunity.microsoft.com/t5/microsoft-defender-blog/vulnerability-shielding-protect-the-time-before-the-patch/ba-p/4572135))

Microsoft Perception, the agentic security platform that orchestrates red, blue and green team agents through playbooks, is now generally available, and the agent inventory is worth knowing by name because these are the things that will be triaging your queue. Generally available: the Alert Triage Agent, Attack Investigation Agent, Detection Authoring Agent and Threat Intelligence Agent on the blue side, the Recon Agent on the red side, and the Posture Prioritization Agent on the green side. In preview: the Risk Reduction Agent, the Web App Pen Test Agent and vulnerability shielding. Humans set guardrails and approve high-impact actions, automated triggers launch playbooks when incidents meet defined criteria, and there are cost dashboards and an estimator because AI usage is now a line item you will be asked about. The case Microsoft makes for all of this rests on three numbers: more than 96,000 vulnerabilities published to CVE in 2026 against roughly 40,000 in 2024, only 26 percent of CISA KEV entries remediated during 2025, and a working weaponised exploit for PHP2Shell appearing roughly a day after disclosure. ([Security for the agentic era, powered by Microsoft Perception](https://www.microsoft.com/en-us/security/blog/2026/11/17/security-for-the-agentic-era-powered-by-microsoft-perception/))

The research item of the week is device code phishing aimed at AI coding agents, and it is the one to take to your developers. In a controlled lab, Microsoft started a GitHub OAuth device-authorization request from an attacker-controlled client, sent the short user code and the genuine github.com verification link to a target under an IT or Copilot-licence pretext, and on approval received a token with the scopes it had asked for — repo, read:user, read:org, gist and codespace. The domain gives no assurance because the page really is hosted by GitHub. What the token then bought, each conditional on a feature being enabled, was remote steering of the victim's GitHub Copilot CLI session, poisoned entries written through the agent's /memory command that influence later sessions, readable cloud-synced session history from before the compromise, and access to private repositories. Mapped to T1566.002 and T1528. Two new Defender XDR detections ship for this, named Suspected GitHub Copilot CLI device code phishing via email and via Microsoft Teams, and they depend on the GitHub Enterprise Cloud connector in Defender for Cloud Apps being in place at enterprise level, so connect it before you need it. For Enterprise Managed Users, disruption suspends the managed identity through the identity provider; for everyone else the response is revoking the OAuth authorization, reviewing synced sessions and repositories, and clearing saved memory, noting that disabling memory does not delete what is already there. The user-facing rule is one sentence: enter a device code only for a sign-in you started yourself. ([The risks of device code authentication for AI coding agents](https://www.microsoft.com/en-us/security/blog/2026/11/17/the-risks-of-device-code-authentication-for-ai-coding-agents/))

Defender Antivirus is getting a clipboard monitor, and it is the most concrete endpoint protection in the release. ClickFix attacks — the fake CAPTCHA or error message that talks a user into pasting a command — accounted for 12.8 percent of all intrusions Microsoft Defender observed between June 2025 and June 2026, with a 23-fold increase in volume between December 2025 and May 2026, and they evade surface-specific blocking by targeting command terminals, Windows Run, Explorer and common file dialogs in turn. A new component, DefenderSessionHelper.exe, detects malicious commands copied from web content before they reach any execution surface and clears the clipboard to break the chain. Remediation is rolling out to all devices running Defender Antivirus and is due to complete by the end of the year, and detections surface in the Defender portal and advanced hunting. Three operational items land alongside it: a new endpoint health dashboard in public preview over the coming weeks covering inventory, cloud communication, antivirus service health and update status with exportable device lists; safe deployment settings that let you stage Defender platform and engine updates across Windows and Linux and enable individual preview features on your own schedule; and an embedded offboarding experience in the Defender deployment tool with expiring, unique, trackable keys, which matters because Octo Tempest-style intrusions reach for offboarding scripts to switch off defences. Custom data collection also expands on 9 December to Linux file created, deleted and renamed events and to Windows registry key and value events. ([Ignite 2026: What's new in endpoint security](https://techcommunity.microsoft.com/t5/microsoft-defender-blog/ignite-2026-what-s-new-in-endpoint-security/ba-p/4573835))

The Entra announcements are mostly about giving agents identities and then governing them like any other principal, and the parts with SOC consequences are specific. Agent ID now covers the 60 local agent types that Defender and Global Secure Access discover, including Claude Code, OpenAI Codex and GitHub Copilot CLI, so a local coding agent becomes a governable identity rather than a process. Lifecycle management for agent identities is generally available, with an out-of-the-box policy that disables agents inactive for 60 days and checks whether each one still has a human sponsor. Conditional Access can now tell a person apart from a local agent acting on their behalf, so you can block a high-risk agent while its user keeps working, and a new actions and destinations option extends policy from applications down to individual sensitive operations. Conditional Access policy plans, also in preview, let you define intent once and enforce it everywhere rather than maintaining the same requirement across a dozen policies, with templates including ones for agents. On the credential side, high assurance credentials pair passkeys with third-party identity verification at onboarding, before sensitive access and at account recovery, which is the lifecycle gap adversary-in-the-middle phishing actually targets; Microsoft cites a FIDO Alliance figure that 57 percent of organisations still rely on phishable methods. Privileged Identity Management expands to application roles and AI agents, adds session monitoring and recording for Azure and Azure Arc VM connections, and gains a PIM-only mode plus bulk management for cutting standing access. There is also an MCP firewall in preview for policy over agent-to-MCP-server traffic, and Microsoft's own telemetry puts tool and agent abuse at 12 percent of observed attack activity against Azure AI workloads. ([AI is changing access. See how Microsoft Entra helps you stay ahead.](https://techcommunity.microsoft.com/t5/microsoft-entra-blog/ai-is-changing-access-see-how-microsoft-entra-helps-you-stay/ba-p/4556456))

CVE-2026-114938, being called Java4Shell, was publicly disclosed on 17 November, and the Azure Network Security team published upgrade guidance and WAF mitigations the next day. It is a heap memory corruption bug in OpenJDK's hardware-accelerated Base64 decoder: specially crafted Base64 input processed by an affected runtime can crash the application, disclose memory or achieve unauthenticated remote code execution. The affected set is narrower than the name suggests and worth checking before you escalate — unpatched OpenJDK runtimes 17.0.6 and later, including Java 21, 25 and 27, running on x86-64 processors with AVX-512 VBMI support, with ARM64 and x86-64 without that instruction set not known to be affected. Patching the runtime is the fix. The interim Azure WAF mitigations are custom rules for Azure Front Door, Application Gateway and Application Gateway for Containers that block long Base64-looking values in request headers, POST arguments, the query string and the Authorization header, and you need to understand what that means before deploying them: the rules match the shape of Base64, not an exploit, so any application that legitimately carries long encoded values in those positions — tokens, cookies, serialised payloads — will be blocked. Pick only the rules matching where your application actually accepts Base64 input, and test in detection mode first. ([Addressing Java4Shell CVE-2026-114938: upgrade guidance and Azure WAF mitigations](https://techcommunity.microsoft.com/t5/azure-network-security-blog/addressing-java4shell-cve-2026-114938-upgrade-guidance-and-azure/ba-p/4574305))

Microsoft says attackers exploited a flaw in the Entra Connect Health API to read tenant-level metadata, and the detail that shapes the response is that there is nothing to patch and no public advisory to track. The timeline Microsoft gave: the flaw was introduced on 23 July, discovered on 9 November, fixed server-side on 19 November, with the investigation concluding on 20 November and notifications beginning. Exposed, per the notice, were the email addresses of tenant technical contacts and administrator accounts, tenant IDs, display names, initial domain names, country codes and regional information, Entra licence tiers, directory sync status including whether sync was enabled and the last sync timestamp, Connect Health onboarding status, and an expired certificate once used to register Connect Health agents with an internal service decommissioned in late 2024 that the API was still returning. Microsoft states that passwords, password hashes, authentication tokens, valid cryptographic keys, on-premises server and Active Directory topology and Azure subscription information were not exposed, and that it found no unauthorized configuration changes. No CVE has been published, no customer remediation is required, and affected organisations were told through an Azure Service Health security advisory — so check the portal directly rather than following links in any email claiming to be the notification. The practical exposure is a curated list of your administrators' addresses alongside enough tenant detail to make a convincing pretext, so treat this as a targeted phishing warning for privileged accounts, confirm they are on phishing-resistant MFA, and review Entra audit and sign-in logs. Microsoft published read-only scripts at aka.ms/ConnectHealth/scripts that show what the API returns for your tenant today, which is not the same as what was accessed. Microsoft has not said who exploited it, how many tenants were affected, or when the attacks began. ([Microsoft Entra Connect Health flaw exploited to steal tenant data, BleepingComputer, 21 November 2026](https://www.bleepingcomputer.com/news/security/microsoft-entra-connect-health-flaw-exploited-to-steal-tenant-data/))

Two Azure DDoS Protection items landed on 16 November that the last issue missed. Custom policy is now generally available, letting you replace the machine-learning auto-tuning with fixed inbound detection thresholds for TCP, UDP and TCP SYN per protected resource, on both Network Protection and IP Protection SKUs, across public endpoints on virtual machines, scale sets, AKS, Standard Load Balancer, Application Gateway, Azure Firewall and Azure Bastion. ## KQL to try

Released on 17 November during the Optimizely supply-chain compromise, this is a straightforward incident-response query for working out which of your devices reached the domains the public investigation named, and it is the right first query to run rather than a long-term hunt. It looks back three days over DeviceNetworkEvents for RemoteUrl containing 1688360.cc, 5vobauua3ojpklx.icu, eil786npto9u5bq.icu or webshell.lol, then labels what each hit most likely represents — the hit.php and card.php paths on the first domain as cookie, screenshot or card-data exfiltration, track.js as the malicious JavaScript payload, the two .icu domains as iOS exploit routers and webshell.lol as the injection infrastructure — and summarises connections, first and last seen, and the set of domains and activity types per device. Widen the lookback to match when your users could have visited an affected brand's site rather than leaving it at three days, and remember that a hit here means a browser loaded attacker content, which is a user and session to triage rather than a compromised endpoint. ([IC - Optimizely Compromised: Identify Devices that visited the Malicious URLs-Domains — Sergio Albea](https://github.com/Sergio-Albea-Git/Threat-Hunting-KQL-Queries/blob/main/Microsoft_DefenderXDR/%5BIC%5D%20-%20Optimizely%20Compromised%3A%20Identify%20Devices%20that%20visited%20the%20Malicious%20URLs-Domains.md))

```kql
DeviceNetworkEvents 
| where Timestamp > ago(3d) 
| where RemoteUrl contains "1688360.cc" or RemoteUrl contains "5vobauua3ojpklx.icu" or RemoteUrl contains "eil786npto9u5bq.icu" or RemoteUrl contains "webshell.lol" 
| extend ActivityType=case(RemoteUrl contains "1688360.cc" and RemoteUrl contains "hit.php","Potential Cookie & Screenshot Exfiltration",RemoteUrl contains "1688360.cc" and RemoteUrl contains "card.php","Potential Card Data Exfiltration",RemoteUrl contains "1688360.cc" and RemoteUrl contains "track.js","Malicious JavaScript Payload",RemoteUrl contains "1688360.cc","Malicious Payload / Exfiltration Infrastructure",RemoteUrl contains "5vobauua3ojpklx.icu","iOS Exploit Router 1",RemoteUrl contains "eil786npto9u5bq.icu","iOS Exploit Router 2",RemoteUrl contains "webshell.lol","JavaScript Injection Infrastructure","Unknown") 
| summarize Connections=count(), FirstSeen=min(Timestamp), LastSeen=max(Timestamp), Domains=make_set(RemoteUrl,20), ActivityType=make_set(ActivityType,10) by DeviceName, DeviceId
```

Published on 19 November, this hunts the thing that happens immediately after a web application is exploited on Linux, which makes it a good companion to a week whose headline vulnerability is a Java runtime remote code execution. It takes four passes over one day of Defender for Endpoint telemetry and unions them. First, DeviceProcessEvents for processes started directly by nginx or nginx-debug, and for shells launched by nginx that themselves start python, perl, php, nc, socat, curl, wget and the like; command lines matching reverse shell fragments — /dev/tcp, bash -i, mkfifo, base64 -d, piping into sh or bash — are labelled separately and more specifically. Second, DeviceFileEvents for files nginx writes into /tmp, /dev/shm or /var/tmp, which is payload staging. Third and fourth, those written files correlated forward two hours against process events, either executed directly from the temp path or named in a later command line, which is the pair of events that turns a staging write into an execution story. The author's caveats are the ones to act on: legitimate nginx hooks, health checks and deployment scripts that call shells will hit, as will applications that cache uploads in those directories, so correlate with the web application logs before acting; and the blind spot is in-memory payloads and embedded interpreters, which never spawn a child process at all. Interpreter and shell lists are let variables, so trim them to what your estate actually runs. ([Nginx Worker Spawning Shells and Scripting Tools on Linux — Benjamin Zulliger](https://github.com/benscha/KQLAdvancedHunting/blob/main/ThreatHunting/Nginx%20Worker%20Spawning%20Shells%20and%20Scripting%20Tools%20on%20Linux.md))

```kql
let lookback = 1d;
let correlationWindow = 2h;
let correlationBin = correlationWindow / 2.0;
// Set to false if FolderPath contains only the directory in the corresponding table.
let fileFolderPathIncludesFileName = true;
let processFolderPathIncludesFileName = true;
let nginxParents = dynamic(["nginx", "nginx-debug"]);
let shellNames = dynamic(["sh", "bash", "dash", "ash", "zsh", "ksh"]);
let suspiciousTools = dynamic([
    "python", "python3", "perl", "ruby", "php", "node", "lua", "awk", "gawk",
    "nc", "ncat", "netcat", "socat", "openssl", "telnet", "curl", "wget",
    "ssh", "sftp", "busybox"
]);
let reverseShellPatterns = @"/dev/tcp|\bbash\s+-i\b|\bmkfifo\b|\bbase64\s+-d\b|(^|\s)-e\s+/bin/(sh|bash)\b|\|\s*(sh|bash)\b";
let isTempPath = (path:string) {
    path == "/tmp" or path startswith_cs "/tmp/"
        or path == "/var/tmp" or path startswith_cs "/var/tmp/"
        or path == "/dev/shm" or path startswith_cs "/dev/shm/"
};
let fullPath = (folderPath:string, fileName:string, pathIncludesFileName:bool) {
    iff(
        pathIncludesFileName,
        trim_end("/", folderPath),
        iff(
            isnotempty(fileName),
            strcat(trim_end("/", folderPath), "/", fileName),
            ""
        )
    )
};
let processDetections =
    DeviceProcessEvents
    | where Timestamp >= ago(lookback)
    | where ActionType == "ProcessCreated"
    | where InitiatingProcessFileName in~ (nginxParents)
        or (
            InitiatingProcessFileName in~ (shellNames)
            and InitiatingProcessParentFileName in~ (nginxParents)
        )
    | where FileName in~ (shellNames) or FileName in~ (suspiciousTools)
    | extend PatternMatched = ProcessCommandLine matches regex reverseShellPatterns
    | extend AttackMethod = case(
        PatternMatched,
            "Possible reverse shell pattern in nginx-related process",
        InitiatingProcessFileName in~ (nginxParents),
            "Shell or tool started by nginx",
        "Shell or tool started by an nginx child shell"
    )
    | project
        Timestamp,
        DeviceName,
        AttackMethod,
        Reason = strcat(
            "Initiator=", InitiatingProcessFileName,
            " | Parent=", InitiatingProcessParentFileName,
            " | Child=", FileName,
            iff(PatternMatched, " | Suspicious command-line pattern", "")
        ),
        Detail = tostring(ProcessCommandLine),
        Context = tostring(InitiatingProcessCommandLine);
let writtenTempFiles = materialize(
    DeviceFileEvents
    | where Timestamp >= ago(lookback + correlationWindow)
    | where ActionType in ("FileCreated", "FileModified")
    | where InitiatingProcessFileName in~ (nginxParents)
    | where isTempPath(FolderPath)
    | extend FullFilePath = fullPath(
        FolderPath,
        FileName,
        fileFolderPathIncludesFileName
    )
    | project
        DeviceId,
        DeviceName,
        WriteTime = Timestamp,
        FullFilePath,
        OriginalFolderPath = FolderPath,
        WrittenFileName = FileName,
        WriteAction = ActionType,
        WriterCmd = InitiatingProcessCommandLine
);
let tempFileDetections =
    writtenTempFiles
    | where WriteTime >= ago(lookback)
    | project
        Timestamp = WriteTime,
        DeviceName,
        AttackMethod = "Temp file created or modified by nginx",
        Reason = strcat(
            "Action=", WriteAction,
            " | FolderPath=", OriginalFolderPath,
            " | FileName=", iff(isempty(WrittenFileName), "<missing>", WrittenFileName)
        ),
        Detail = tostring(FullFilePath),
        Context = tostring(WriterCmd);
let directTempExecutions =
    writtenTempFiles
    | where isnotempty(DeviceId)
        and isnotempty(WrittenFileName)
        and isnotempty(FullFilePath)
    | join kind=inner (
        DeviceProcessEvents
        | where Timestamp >= ago(lookback)
        | where ActionType == "ProcessCreated"
        | where isnotempty(DeviceId) and isnotempty(FolderPath)
        | where isTempPath(FolderPath)
        | extend FullExecPath = fullPath(
            FolderPath,
            FileName,
            processFolderPathIncludesFileName
        )
        | where isnotempty(FullExecPath)
        | project
            DeviceId,
            FullExecPath,
            ExecTime = Timestamp,
            ExecReportId = ReportId,
            ExecCmd = ProcessCommandLine,
            ExecInitiator = InitiatingProcessFileName,
            ExecParent = InitiatingProcessParentFileName
    ) on DeviceId, $left.FullFilePath == $right.FullExecPath
    | where ExecTime >= WriteTime
        and ExecTime <= WriteTime + correlationWindow
    | summarize arg_max(
        WriteTime,
        DeviceName,
        WriteAction,
        WriterCmd,
        ExecCmd,
        ExecInitiator,
        ExecParent
    ) by DeviceId, ExecTime, ExecReportId, FullFilePath
    | project
        Timestamp = ExecTime,
        DeviceName,
        AttackMethod = "Nginx-created or modified temp path later started on the same device",
        Reason = strcat(
            "Path=", FullFilePath,
            " | File action=", WriteAction,
            " | Process initiator=", ExecInitiator,
            " | Parent=", ExecParent
        ),
        Detail = tostring(ExecCmd),
        Context = tostring(WriterCmd);
let tempFileReferences =
    writtenTempFiles
    | where isnotempty(DeviceId)
        and isnotempty(WrittenFileName)
        and isnotempty(FullFilePath)
    | extend TimeKey = bin(WriteTime, correlationBin)
    | join kind=inner (
        DeviceProcessEvents
        | where Timestamp >= ago(lookback)
        | where ActionType == "ProcessCreated"
        | where isnotempty(DeviceId) and isnotempty(ProcessCommandLine)
        | where ProcessCommandLine has_any ("tmp", "shm")
        | where ProcessCommandLine contains_cs "/tmp/"
            or ProcessCommandLine contains_cs "/dev/shm/"
        | extend
            FullExecPath = fullPath(
                FolderPath,
                FileName,
                processFolderPathIncludesFileName
            ),
            TimeKey = range(
                bin(Timestamp - correlationWindow, correlationBin),
                bin(Timestamp, correlationBin),
                correlationBin
            )
        | mv-expand TimeKey to typeof(datetime)
        | project
            DeviceId,
            ExecTime = Timestamp,
            TimeKey,
            ExecReportId = ReportId,
            FullExecPath,
            ExecCmd = ProcessCommandLine,
            ExecInitiator = InitiatingProcessFileName,
            ExecParent = InitiatingProcessParentFileName
    ) on DeviceId, TimeKey
    | where ExecTime >= WriteTime
        and ExecTime <= WriteTime + correlationWindow
    | where ExecCmd contains_cs FullFilePath
    | where FullExecPath != FullFilePath
    | summarize arg_max(
        WriteTime,
        DeviceName,
        WriteAction,
        WriterCmd,
        ExecCmd,
        ExecInitiator,
        ExecParent
    ) by DeviceId, ExecTime, ExecReportId, FullFilePath
    | project
        Timestamp = ExecTime,
        DeviceName,
        AttackMethod = "Nginx-created or modified temp path mentioned in a later command line",
        Reason = strcat(
            "Path substring=", FullFilePath,
            " | File action=", WriteAction,
            " | Process initiator=", ExecInitiator,
            " | Parent=", ExecParent
        ),
        Detail = tostring(ExecCmd),
        Context = tostring(WriterCmd);
union processDetections, tempFileDetections, directTempExecutions, tempFileReferences
```

## Worth knowing

If post-quantum cryptography has been sitting in your someday pile, Microsoft's Ignite write-up is a decent place to start because it separates the two halves of the problem cleanly. Key exchange is the urgent half, because harvest-now-decrypt-later needs no quantum computer today to create a problem later, and it is the half you can act on: the October 2026 security update adds pure post-quantum key exchange and authentication to the Windows TLS stack on Windows 11 24H2 and later and Windows Server 2025, building on the hybrid key exchange shipped earlier in the year, and Microsoft recommends starting with hybrid ML-KEM rather than pure unless a requirement says otherwise. Authentication is the slower half because it needs the whole certificate ecosystem to move; ML-DSA X.509 certificates give enterprise PKI and service-to-service scenarios somewhere to start, Active Directory Certificate Services already supports ML-DSA and will add composite certificates so classical and post-quantum trust can run side by side, and for the Web PKI the IETF is working on Merkle Tree Certificates to deal with signature size at scale. The realistic first task is neither of those: identify the data that must stay confidential for years, then map the applications and certificate dependencies that will have to change. ([Preparing for a Post-Quantum Future with TLS in Windows](https://techcommunity.microsoft.com/t5/microsoft-security-community/preparing-for-a-post-quantum-future-with-tls-in-windows/ba-p/4572619))
