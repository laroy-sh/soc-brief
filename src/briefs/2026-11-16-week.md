## Act by

- **12 November 2027** — support for Microsoft Purview Data Governance ends, and Microsoft Fabric becomes the data governance product. A year sounds like plenty until you remember what a catalogue migration touches: policies, lineage, stewardship assignments and whatever reporting your compliance team built on top of them. Microsoft says transition guidance is available as of 12 November 2026 and that organisations with contractual obligations or in regulated industries should engage their account team early rather than treat this as a self-service move. Note the boundary Microsoft is drawing while you plan: Purview keeps data security and compliance — classification, labelling, data loss prevention — and only governance moves to Fabric, so this should not turn into a review of your DLP estate unless you want one. ## What changed

Microsoft 365 went down for several days from 12 November — a network capacity problem, not an attack — and the phishing followed almost immediately. Microsoft Threat Intelligence published the details on 14 November, and the part that makes this campaign land is that it cites the genuine Exchange Online incident ID, EX1550543, so a recipient who checks the reference finds that it is real. Messages Microsoft detected on 13 November claim mail was held during the outage and will be deleted within 24 hours unless the recipient clicks to restore it. Subjects follow the pattern "Outage - [six-character code]", sender display names use an organisation-specific prefix followed by "Outage Notification" or "Service Health", and the sender domains are moments-notice[.]com, planetmaison[.]com and newbooker[.]com, with recipient-specific SendGrid click-tracking links redirecting to reallifeaccounting[.]com, path /themelist0.html observed. Microsoft describes the activity as consistent with credential phishing but has not confirmed credential collection or malware delivery, and points at Threat Explorer plus EmailEvents, EmailUrlInfo and UrlClickEvents for the hunt. Verify Safe Links policies while you are there, and tell your service desk that outage notifications are now a phishing lure. ([Microsoft Threat Intelligence, 14 November 2026](https://x.com/MsftSecIntel/status/2121491564161581148))

November's Patch Tuesday landed on 10 November with exactly one vulnerability flagged as exploited, and it is one that a severity-driven triage queue will push to the bottom. CVE-2026-124194 is a Microsoft Outlook spoofing vulnerability rated Moderate, CVSS 6.5, and the FAQ explains what it actually does: an attacker sends a crafted message file, the user opens it, Outlook connects to an attacker-controlled network location without the usual external-content warning, and the user's NTLMv2 hash goes with it. That is a credential-relay primitive delivered by email with no privileges required. Two details shape the response. The preview pane is not an attack vector, so the user has to open the file, which means awareness messaging is worth something here. And the affected products are Microsoft 365 Apps for Enterprise and Office LTSC 2021 and 2024, so this is a client-side patching job across your estate rather than a server change. Nothing else in the release was publicly disclosed before patch day. ([Microsoft Security Update Guide](https://msrc.microsoft.com/update-guide/releaseNote/2026-Nov))

The shape of the rest of the November release matters for how you plan the month. The release document carries 1,644 CVE entries, of which 1,096 were first published on 10 November itself; 63 of those new ones are rated Critical and 42 carry an Exploitation More Likely rating, which is the far more useful filter than severity when the list runs to four figures. Two of the Criticals deserve naming. CVE-2026-116928 is a Windows Search remote code execution bug, CVSS 9.8, and the exploitation path runs through Exchange Server: an email with a crafted attachment is automatically processed for indexing, so the recipient never has to open anything. CVE-2026-119958 is an out-of-bounds write in Windows LDAP, also 9.8, unauthenticated code execution in the context of the LDAP service. Alongside those, CVE-2026-118146 in Active Directory Domain Services and CVE-2026-118207 in Exchange Server are both 8.8, both need only low-privileged authentication, and both are rated Exploitation More Likely — which is the combination that decides what a domain controller and mail server patching window looks like this month. CVE-2026-119990, an Azure OpenAI elevation of privilege rated 9.8, needs no action from you; it is a cloud service CVE published for transparency and Microsoft has already mitigated it. ([Microsoft Security Update Guide](https://msrc.microsoft.com/update-guide/releaseNote/2026-Nov))

Microsoft Threat Intelligence confirmed and extended ConnectWise's 11 November report of threat actors reaching cloud-hosted ScreenConnect instances belonging to managed service providers, and the worm it documents, SCKit, is built around an idea worth internalising: the customer endpoint attacks the technician. Deployment starts with commands issued through the legitimate console that use curl to pull a second ScreenConnect MSI into C:\Windows\Temp and install it silently against attacker infrastructure, so securing the approved console does not remove the second channel. A batch launcher then fetches a PowerShell decoder that derives a key from the machine's MachineGuid, decrypts an AES-256-CBC bundle and extracts it to %TEMP%\SCKitBundle. The component to hunt for is RelayTrap: scripts under C:\ProgramData\RelayTrap, a RelayTrapLiteAlert value in the machine-wide Run key, and a scheduled task running a watcher that polls every 10 seconds, compiling a replacement client from the real ScreenConnect libraries so that it can push a payload into a technician's session when one connects. From the technician side the kit goes after .ASPXAUTH cookies in Chrome, Edge, Opera and Opera GX, by database query with a volume shadow copy fallback and by scanning browser network-service process memory, then uses the stolen console session to distribute payloads through the Shared Toolbox. Three operational points from Microsoft's guidance: investigate out-of-band using Defender for Endpoint live response rather than ScreenConnect, revoke exposed web sessions from a clean device because password changes alone do not invalidate them, and do not run the cleanup script found in the kit, which re-arms the dropper unless -NoReArm is set. ([SCKit abuses ScreenConnect to deploy remote access and target technician sessions](https://www.microsoft.com/en-us/security/blog/2026/11/13/sckit-abuses-screenconnect-deploy-remote-access-target-technician-sessions/))

The second intrusion write-up of the week is the one to take to whoever owns your Linux estate, because it is an argument against calling a web application compromise closed when the application is patched. Microsoft has observed multiple incidents where threat actors deployed GSocket, an open source relay tool, on compromised Linux servers and kept access after the original vulnerability was fixed. There is no attacker-owned address or domain to block: both the compromised host and the operator connect outbound to the public Global Socket Relay Network, which pairs them by shared secret over an encrypted channel, so no inbound listener, no public IP and no permissive firewall rule are needed. Defender for Endpoint telemetry shows devices with GSocket-related detections up 356.2 percent from March to August 2026, with web applications and hosting accounting for 87.1 percent of attributable incidents — PHP applications and cPanel hosting 63.9 percent of those, Apache 24.3 percent — and education and research the largest affected sector at 30.7 percent. The tradecraft is modest and specific: curl fetches a staging script, the client is staged in writable or memory-backed paths such as /dev/shm, the process is renamed to look like a kernel thread, persistence is layered across cron, systemd, shell profiles and watchdogs, and in some incidents the actors tried CVE-2026-43284 to reach root. Deny-by-default egress, non-executable /dev/shm where you can manage it, and an audit of persistence surfaces are the controls that help; blocking an address does not. ([The global socket: how threat actors are weaponizing GSocket for stealthy C2](https://www.microsoft.com/en-us/security/blog/2026/11/11/global-socket-how-threat-actors-weaponizing-gsocket-stealthy-c2/))

Microsoft Defender Research and the AI Red Team published two studies on poisoning the post-training supply chain for coding agents, and the numbers are high enough that this stops being hypothetical. In the dataset poisoning study, 90 crafted examples hidden in roughly 9,000 terminal-agent conversations — about one percent of the corpus — taught a fine-tuned gpt-4.1-mini to respond to an ordinary request to create project documentation by inspecting the available tools, finding whichever one can execute commands, and issuing a schema-valid call that fetches and runs attacker content. Success was 78.0 and 77.8 percent on the two harnesses seen during training and 11.0 percent on an unseen one, and crucially it generalised to paraphrases of the trigger at 52 to 70 percent, so exact-string detection does not catch it. The model poisoning study, where the adversary controls training and distributes the checkpoint, reached 84.1 to 94.8 percent on unseen repositories and survived additional reinforcement learning that restored benign performance. The team also found rows in a large public dataset mapping benign requests to a tool call that curls and sources a remote script — intent unknown, but it demonstrates that a dataset's size and reputation prove nothing. The practical ask is dull and doable: review training data by comparing the user request against the assistant action rather than only checking format, require checkpoint provenance, and keep agent tool permissions tight, because the tools define the blast radius. ([Trained to betray: How post-training supply chain attacks hijack coding agents](https://www.microsoft.com/en-us/security/blog/2026/11/12/trained-to-betray-how-post-training-supply-chain-attacks-hijack-coding-agents/))

In the same vein and two days earlier, Microsoft Research showed that editing fewer than 10 neurons in a capable agent model is enough to implant a sleeper agent that passes evaluation and then executes an attacker's command when a trigger string appears in context. The attack needs only inference-level compute — if a machine can run the model, it can backdoor it — and Microsoft has not observed anyone using the technique. What makes this an operations item rather than a research curiosity is the detection result and the mitigations attached to it. Implanted neurons change a few weight vectors by a large amount while legitimate fine-tunes and quantisations change weights broadly, so diffing every checkpoint against its declared base model and flagging statistical outliers works, and frontier models are effective auditors for exactly this. The containment advice is the part most SOCs can act on without an ML team: give each agent its own Entra Agent ID with least-privilege scope, use Conditional Access for agents, run agent-generated code only in isolated sandboxes, apply egress controls to inference hosts, and turn on AI model security in Defender for Cloud to scan models in Azure Machine Learning workspaces and registries — with the caveat Microsoft states plainly, that this catches serialisation and code-level risks and does not replace a weight-level audit. ([Detecting sleeper agents hiding in AI model neurons](https://www.microsoft.com/en-us/security/blog/2026/11/10/detecting-sleeper-agents-hiding-in-ai-model-neurons/))

Ahead of Ignite, the Sentinel team published its connector round-up: roughly fifty new and enhanced partner integrations described in detail, plus another twenty or so listed by name, against a platform total now past 500. Most of it is catalogue, but three entries are worth a look if they match tooling you already own. BloodHound Enterprise now feeds identity attack path data and posture insights into Sentinel, which turns "we know we have attack paths" into something you can join against detections. And Pulumi Cloud audit logs arrive with three analytics rules covering failed logins, stack deletions and organisation membership changes, which is one of the first connectors framed explicitly around telling you what a human or an agent did to your infrastructure as code. Several of the new integrations are AI-agent oriented, including one bringing prompt injection and suspicious tool usage signals into Sentinel incident workflows. ([Microsoft Ignite 2026: New Sentinel Connectors Announcement](https://techcommunity.microsoft.com/t5/microsoft-sentinel-blog/microsoft-ignite-2026-new-sentinel-connectors-announcement/ba-p/4565258))

## KQL to try

Published on 10 November, this is a well-constructed hunt for the DLL hijacking paths that privileged Windows components keep falling into, and it is the rare query that correlates the staging step with the payoff rather than alerting on either alone. It looks over two hours for a write, create or rename of Printconfig.dll under the Print Spooler driver directory, tzres.dll under WBEM, or phoneinfo.dll in System32 — the exact paths those components load from — where the writing process ran at low, medium or untrusted integrity and the account is not SYSTEM, LOCAL SERVICE or NETWORK SERVICE. It then checks DeviceImageLoadEvents over the following hour for the same device, path and SHA1 being loaded by a process running as one of those service accounts within 30 minutes of the write, and labels which of the three paths fired. A match is a low-privileged write followed by a privileged load of the identical file, which is local privilege escalation rather than a benign file operation. The author's own caveat is the one to check first: if either event type is missing a SHA1 in your environment, the join silently produces false negatives. ([DLL Hijacking via Print Spooler, WBEM and WER Paths — Benjamin Zulliger](https://github.com/benscha/KQLAdvancedHunting/blob/main/ThreatHunting/DLL%20Hijacking%20via%20Print%20Spooler,%20WBEM%20and%20WER%20Paths.md))

```kql
let SuspiciousWrites =
    DeviceFileEvents
    | where Timestamp >= ago(2h)
    | where ActionType in ("FileCreated", "FileModified", "FileRenamed")
    | where FileName in~ ("Printconfig.dll", "tzres.dll", "phoneinfo.dll")
    | where FolderPath matches regex @"(?i)^[a-z]:\\windows\\system32\\(spool\\drivers\\(x64|w32x86)\\3\\printconfig\.dll|wbem\\tzres\.dll|phoneinfo\.dll)$"
    | where InitiatingProcessIntegrityLevel in~ ("Low", "Medium", "Untrusted")
    | where isnotempty(InitiatingProcessAccountSid)
    | where InitiatingProcessAccountSid !in ("S-1-5-18", "S-1-5-19", "S-1-5-20")
    | where isnotempty(SHA1)
    | project DeviceId,
        DllPath = tolower(FolderPath),
        PayloadSHA1 = tolower(SHA1),
        WriteTime = Timestamp,
        WriteAction = ActionType,
        WriterAccountSid = InitiatingProcessAccountSid,
        WriterAccount = strcat(InitiatingProcessAccountDomain, @"\", InitiatingProcessAccountName),
        WriterProcess = InitiatingProcessFileName,
        WriterCommandLine = InitiatingProcessCommandLine,
        WriterIntegrity = InitiatingProcessIntegrityLevel,
        WriterProcessUniqueId = InitiatingProcessUniqueId;
DeviceImageLoadEvents
| where Timestamp >= ago(1h)
| where FileName in~ ("Printconfig.dll", "tzres.dll", "phoneinfo.dll")
| where InitiatingProcessAccountSid in ("S-1-5-18", "S-1-5-19", "S-1-5-20")
| where isnotempty(SHA1)
| project Timestamp, DeviceId, DeviceName, ReportId, FileName,
    DllPath = tolower(FolderPath),
    PayloadSHA1 = tolower(SHA1),
    LoaderProcess = InitiatingProcessFileName,
    LoaderCommandLine = InitiatingProcessCommandLine,
    LoaderAccountSid = InitiatingProcessAccountSid,
    LoaderProcessUniqueId = InitiatingProcessUniqueId
| join kind=inner SuspiciousWrites on DeviceId, DllPath, PayloadSHA1
| where Timestamp >= WriteTime and Timestamp <= WriteTime + 30m
| summarize arg_max(WriteTime, *) by Timestamp, DeviceId, ReportId
| extend AttackPath = case(
    FileName =~ "Printconfig.dll", "Print Spooler DLL hijacking",
    FileName =~ "tzres.dll", "WBEM DLL hijacking",
    "WER phoneinfo.dll hijacking")
| project Timestamp, DeviceId, DeviceName, ReportId, AttackPath,
    DllPath, PayloadSHA1, WriteTime, WriteAction,
    WriterAccount, WriterAccountSid, WriterProcess, WriterCommandLine,
    WriterIntegrity, WriterProcessUniqueId,
    LoaderProcess, LoaderCommandLine, LoaderAccountSid, LoaderProcessUniqueId
```

Released on 16 November as part of a set built around agentic offensive frameworks, this one hunts connections to out-of-band testing and disposable callback services — webhook.site, the interactsh family, burpcollaborator.net, oastify.com, requestbin.net, pipedream.net and others — which automated offensive tooling uses to confirm blind vulnerabilities and receive data. It parses the host out of RemoteUrl in DeviceNetworkEvents, adding a scheme only when one is missing, matches against the list, and summarises per device, process and account in hourly bins. The author is explicit that these domains are dual-use and that the thresholds are starting points, so run it as a hunt and exclude your application security and pentest machines first. The triage rule in the query's own notes is the one worth keeping: identify the process making the callback, and if the device is a server, treat the callback as possible successful exploitation rather than as testing noise. ([OAST, Webhook, and Disposable Callback Destinations — Ali Hussein](https://github.com/0xAnalyst/DefenderATPQueries/blob/main/Offensive%20AI%20Agents/C2_OAST_Webhook_Callback_Domains.md))

```kql
let CallbackDomains=dynamic(["webhook.site","interact.sh","oast.pro","oast.live","burpcollaborator.net","oastify.com","oast.site","oast.online","oast.fun","oast.me","requestbin.net","pipedream.net"]);
DeviceNetworkEvents
| where Timestamp > ago(7d)
| where isnotempty(RemoteUrl)
| extend Host=tolower(tostring(parse_url(iff(RemoteUrl matches regex @"(?i)^https?://", RemoteUrl, strcat("https://",RemoteUrl))).Host))
| where Host has_any (CallbackDomains) or RemoteUrl has_any (CallbackDomains)
| summarize Connections=count(), UniqueDestinations=dcount(RemoteUrl), SampleDestinations=make_set(RemoteUrl,10) by DeviceId, DeviceName, InitiatingProcessFileName, InitiatingProcessAccountName, bin(Timestamp,1h)
| order by Connections desc
```

## Worth knowing

The GSocket write-up points at a companion piece published the same day, and it is the better answer to "how urgent is local privilege escalation patching on an internet-facing Linux server". Microsoft's FORGE Lab scanned a subset of Linux kernel subsystems from late May to mid-June 2026 with two people and an AI pipeline, producing 26,502 raw findings in about two weeks, which filtering and reproduction reduced to 621 cases with proof-of-concept evidence and then 59 public upstream reports and 33 assigned CVEs. Twenty-four of those CVEs are rated High or above, and the team confirmed working local root privilege escalation exploits for eight of them, spanning IPv6 fragmentation, rhashtable walks, IPsec routing, the GTP tunnel driver and encrypted key updates. The detail that should change how you think about kernel patch backlogs is the age: the average reported bug had been in the kernel for 8.1 years when it was first reported, six were 15 to 19 years old, and one shift-out-of-bounds bug in cls_u32 had been there for at least 21 years. Getting fixes merged took a median of 41 days from first public patch, and only 38 of the 59 reports have landed in mainline so far. ([Lessons from 59 Linux Kernel Bug Reports](https://www.microsoft.com/en-us/security/blog/2026/11/11/lessons-from-59-linux-kernel-bug-reports/))
