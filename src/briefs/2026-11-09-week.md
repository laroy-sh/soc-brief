## Act by

- **December 2026** — Emergency Mitigation Service 2.0 is due for Exchange Server and Skype for Business Server, enabled by default and with a wider mitigation set than the service you have today; SharePoint Server follows in January 2027. The thing to do before it arrives rather than after is the change-management conversation: Microsoft is describing a service that applies interim mitigations to a production mail server automatically while a permanent fix is prepared, and the people who will be paged when a mitigation changes behaviour should know that it is coming and have agreed it is acceptable. Inventory which on-premises Exchange, SharePoint and Skype for Business servers you still run, confirm whether Emergency Mitigation Service is currently reachable from them, and decide your position on automatic mitigation now. ([New investments to reduce on-premises security risk](https://techcommunity.microsoft.com/blog/microsoft-security-blog/new-investments-to-reduce-on-premises-security-risk/4570381))

## What changed

Microsoft Threat Intelligence published the clearest picture yet of what an AI agent actually does with a stolen application credential, and the timings are the part to take to your incident review: in one case an agent went from searching GitHub for secrets to exfiltrating data from Azure Key Vault in about five minutes. Large volumes of GitHub secret-search queries from the ARTEX framework have been running since August 2026, and the earliest observed successful service principal sign-ins were on 28 October from 199.19.77[.]84; in some tenants the credential used belonged to a vendor's multitenant application, which then gave access to downstream tenants. The behaviour that defeats ordinary tuning is adaptive retry — when an Azure Resource Manager call failed on an unsupported API version the agent changed the version or the HTTP method and got an HTTP 200 roughly 28 to 80 seconds later, so a failed control-plane call is no longer evidence that the attempt stopped. Microsoft's hunting guidance is worth lifting wholesale: AADSTS7000215 or AADSTS7000222 failures followed by a success, one address authenticating to three or more service principals with mixed results, and a single application requesting tokens across Resource Manager, Key Vault, Storage and Graph inside a short window. ([Threat actors use agentic AI tooling to find and abuse exposed secrets](https://www.microsoft.com/en-us/security/blog/2026/11/05/threat-actors-use-agentic-ai-tooling-to-find-and-abuse-exposed-secrets/))

A day later Microsoft attributed a second strand of ARTEX activity to Storm-3358, a financially motivated, Cambodia-based cluster that started using the framework against financial organisations in October 2026, mainly in Southeast Asia and to a lesser extent against large financial firms globally. The chain is unglamorous and quick: exploit an anonymous file upload or server-side request forgery flaw on an internet-facing system, pull a remote access trojan down with netcat or curl, then persist and move with WISP, vshell or AdaptixC2. This is one of the rare reports where the indicator table is worth loading the day you read it, because Microsoft lists command-and-control and ARTEX server addresses that were still active on the publication date, and it ships both a Defender XDR query for newly curl-downloaded files against a seven-day baseline and a Sentinel ASIM query for the address set. One defect to carry across: the Sentinel query lists 178.15.54.129 while the indicator table lists 178.16.54.129, so decide which you mean before you deploy either. ([ARTEX abuse expands as cybercriminals target financial sector](https://www.microsoft.com/en-us/security/blog/2026/11/06/artex-abuse-expands-as-cybercriminals-target-financial-sector/))

Microsoft opened a named programme for on-premises server risk, and the concrete part for anyone still running Exchange, SharePoint or Skype for Business Server is On-Premises Baseline Security Mode — an attempt to ship those products with a validated secure-by-default configuration while leaving administrators in control. Three strands have dates. Since September 2026 Microsoft releases Important security updates outside Patch Tuesday rather than only Critical ones, which quietly changes the assumption that out-of-band means drop everything. Emergency Mitigation Service 2.0 lands in December 2026 for Exchange and Skype for Business and in January 2027 for SharePoint, and Q1 2027 is the stated target for hardened default configurations, detection of drift away from that baseline, and automatic application of security updates after a fixed period in connected environments. ([New investments to reduce on-premises security risk](https://techcommunity.microsoft.com/blog/microsoft-security-blog/new-investments-to-reduce-on-premises-security-risk/4570381))

The quarterly email report is mostly volume numbers, but one of them is a finding about your tenant rather than about attackers: in September, overrides applied to 63 percent of messages that had a recorded security outcome, and most of those were tenant-level overrides. Set against roughly 7.3 billion email phishing threats for the quarter and nearly 3 billion in September alone, up 41 percent on August, that is a very large population of messages whose fate your own allow lists decided. The technique mix moved as well — QR code phishing fell 67 percent from the second quarter while SVG attachments returned and drove payload attacks to 10.1 million in August, the highest monthly figure in over a year, and Teams impersonation drifted away from obvious help desk identities, with personal-name display names rising from 46 to 88 percent of sampled malicious calls between July and September. The homework Microsoft puts first is the exception review, and it is the right order: find the tenant-level overrides nobody owns and remove them before tuning anything else. ([Email threat landscape: Q3 2026 trends and insights](https://www.microsoft.com/en-us/security/blog/2026/11/05/email-threat-landscape-q3-2026-trends-and-insights/))

A fake-download campaign aimed at people searching for cracked software, game executors, activators and unofficial utilities is delivering several monetised payloads in a single installation session: proxyware that routes traffic through the victim's machine, BOINC and CharityEngine for distributed compute, and adware-style utilities. The durable detection is not the lure filename but the staging pattern — execution out of %TEMP%\is-\*.tmp, numbered eld\*.exe and set\_\*.exe stages, Inno installer arguments such as /SL5 and /SPAWNWND, and outbound callbacks carrying d=inno together with r=offer\_execution. Three SYSTEM-level scheduled tasks are the persistence worth hunting, one of which runs a hidden PowerShell script every five minutes, and because some child processes launch before the callback the callback is not a reliable prevention point. If an attack surface reduction discussion has been sitting in your backlog, the rule that blocks executables lacking prevalence, age or trust criteria is the one that would have caught this. ([Fake-download campaign uses trojanized installers to deliver monetization payloads](https://www.microsoft.com/en-us/security/blog/2026/11/03/fake-download-campaign-uses-trojanized-installers-deliver-monetization-payloads/))

The Entra November release moves three authentication changes to general availability, and together they change what a first enrolment looks like. Users can register a passkey or another passwordless option as their first MFA method, with rollout continuing through February 2027, which removes the long-standing awkwardness of standing up a phone-based method in order to reach the phishing-resistant one. Windows Hello for Business and macOS Platform SSO also become standalone MFA factors, qualifying for step-up prompts, Authentication Strength and sign-in frequency checks without a passkey, with rollout beginning in early November 2026 — worth knowing before someone reports that a Conditional Access policy started behaving differently. The third is Microsoft Authenticator passkey backup and restore on Android from January 2027, which requires Google One backup and a screen lock and applies only to personal profiles. ([What's new in Microsoft Entra: November 2026](https://techcommunity.microsoft.com/blog/microsoft-entra-blog/what%E2%80%99s-new-in-microsoft-entra-november-2026/4556457))

Also in that release, and more consequential than its preview label suggests: lifecycle management for agent identities. It brings policy guardrails for reconfirmation intervals, sponsor requirements and inactivity monitoring, and there is a default policy available to every tenant with no licence required that notifies the owner after 60 days of inactivity and disables the identity if no new activity follows. If you have been arguing internally that nobody owns the agent identities accumulating in your tenant, this is the mechanism that produces the list — and the default policy means it will start producing it whether or not anyone configures anything. ([What's new in Microsoft Entra: November 2026](https://techcommunity.microsoft.com/blog/microsoft-entra-blog/what%E2%80%99s-new-in-microsoft-entra-november-2026/4556457))

Two identity governance previews from the same release belong on a backlog rather than in this week's work. Drift detection for access package entitlements flags over-granted permissions and missing assignments with reports that refresh daily, and needs Entra ID Governance or the Entra Suite. Application group discovery extends account discovery to groups created directly inside connected applications and classifies them as local, unassigned or assigned, which is the kind of visibility that turns a SaaS access review from a round of interviews into a query. ([What's new in Microsoft Entra: November 2026](https://techcommunity.microsoft.com/blog/microsoft-entra-blog/what%E2%80%99s-new-in-microsoft-entra-november-2026/4556457))

Carried over from the Monday that closed last week's issue: Private Access and Internet Access can be bought together as Microsoft Entra Global Secure Access, effective 2 November. The packaging is not the interesting part — both remain available separately, and Global Secure Access also sits inside the Entra Suite and Microsoft 365 E7 — but the post is the clearest single statement of where the network-side features now stand. Generally available: custom headers in Internet Access, Purview data security enforced at the network layer, connector load balancing with session affinity, and device and risk signals for Universal Continuous Access Evaluation, which triggers reauthentication within about two minutes when a device becomes noncompliant or disabled or user risk goes high. In public preview: cloud firewall for Global Secure Access clients, a Continue default action for web content filtering, home network support for Private Access, TLS inspection with Microsoft-managed certificates, multiple traffic forwarding profiles for Private Access, and health and alerts. ([Global Secure Access: Private Access and Internet Access in one offering](https://techcommunity.microsoft.com/blog/microsoft-entra-blog/global-secure-access-private-access-and-internet-access-in-one-offering/4569098))

Microsoft Execution Containers reached general availability, giving Windows an operating-system-enforced containment layer for AI agents with least-privilege controls over files, networks, processes and user interactions. Integration with Intune, Entra and Agent 365 is described as upcoming, so for now this is a capability you adopt host by host rather than something you govern from a console. Announced alongside it, and without stated availability, is the access model Microsoft intends to pair with containment: Dynamic Permissions scoped to an agent's current task and lasting only as long as that task, Dynamic Agent Risk reassessing whether the granted authority still matches the agent's behaviour and context, and Dynamic Conditional Access responding by narrowing permissions or requiring human approval for higher-impact actions. ([What's new in Microsoft Security: November 2026](https://www.microsoft.com/en-us/security/blog/2026/11/05/whats-new-in-microsoft-security-november-2026/))

Defender for SQL Servers on Machines now supports Azure Arc SQL Server instances with Arc proxy enabled, from Defender for SQL extension version 2.0.3585.403, so estates that forbid direct outbound internet access from database hosts can tunnel that communication through Arc proxy and still use every feature of the plan. Two operational notes matter more than the capability. The version is manual-update only and automatic rollout has deliberately not started, to give you time to look at what the expanded coverage would pick up; and that coverage can add billable resources, so review the Arc proxy-enabled machines now and disable the plan at the resource level for anything you want left out before the rollout reaches you. ([Arc proxy support for Defender for SQL Servers on Machines](https://learn.microsoft.com/en-us/azure/defender-for-cloud/release-notes))

## KQL to try

Published on 5 November and the natural companion to this week's agentic-secrets reporting, this hunt deliberately ignores addresses that rotate and looks for the authentication errors a credential thief generates instead. It unions EntraIdSignInEvents and EntraIdSpnSignInEvents over seven days, filters to error codes 7000215 and 7000222 — invalid client secret and expired client secret — tags which table each row came from, and labels the error. The reason to run it is the sequence rather than any single row: a stale or wrong secret being tried against one of your applications is noise on its own, and an urgent lead when a success follows shortly after from the same place. The author cites the same Todyl investigation into stolen application credentials signing into Entra ID and Azure DevOps that sits behind Microsoft's own write-up. ([Hunting for Suspicious Client Secret Authentication Attempts — Sergio Albea](https://github.com/Sergio-Albea-Git/Threat-Hunting-KQL-Queries/blob/main/Microsoft_DefenderXDR/EntraIdSignInEvents/Hunting%20for%20Suspicious%20Client%20Secret%20Authentication%20Attempts.md))

```kql
let UserSignIns = EntraIdSignInEvents
| where Timestamp > ago(7d) | where ErrorCode in (7000215, 7000222)
| project Timestamp, SourceTable = "UserSignIns", Application, IPAddress, Country, ErrorCode;
let SpnSignIns = EntraIdSpnSignInEvents | where Timestamp > ago(7d) | where ErrorCode in (7000215, 7000222)
| project Timestamp, SourceTable = "ServicePrincipalSignIns", Application, IPAddress, Country, ErrorCode;
union UserSignIns, SpnSignIns
| extend ErrorDescription = case(ErrorCode == 7000215, "Invalid client secret", ErrorCode == 7000222, "Expired client secret", "Other")
```

Also from 5 November, a preparation query rather than a detection: Node.js has announced security releases for 11 November covering several vulnerabilities including high-severity ones, and this reads DeviceTvmSoftwareInventory to find where Node.js is installed and which major version each device is on. It extracts the major version, classifies it as Active LTS, Maintenance LTS, Alpha or End of Life, derives a patch-readiness string from that, and assigns a priority that puts end-of-life installations first and supported versions awaiting the 11 November update third. The useful output is the first bucket — end-of-life majors that will not receive the update at all and therefore need migration rather than patching — and the honest caveat is that the version-to-support mapping is the author's and is accurate for the release train as it stood when this was written. ([Identify Node.js installed versions ahead of the 11 November high-severity Node.js vulnerabilities — Sergio Albea](https://github.com/Sergio-Albea-Git/Threat-Hunting-KQL-Queries/blob/main/Microsoft_DefenderXDR/Identify%20Node.js%20installed%20Versions%20with%20queries%20to%20patch%20on%20Novembrer%2011%20HIGH-Severity%20Node.js%20Vulnerabilities.md))

```kql
DeviceTvmSoftwareInventory | where SoftwareName contains "node.js" or SoftwareName contains "nodejs" 
| extend MajorVersion = toint( extract(@"^v?(\d+)", 1, SoftwareVersion)) 
| extend SupportStatus = 
case( MajorVersion == 26, "Active LTS", MajorVersion in (22, 24), "Maintenance LTS",     MajorVersion == 27, "Alpha",     MajorVersion in (25, 23, 21, 20, 19, 18, 17, 16, 15, 14, 13, 12, 11, 10, 9, 8, 7, 6, 5, 4, 0), "End of Life", "Unknown") 
| extend PatchReadiness = 
case( SupportStatus == "End of Life", "Migration required - No official security patches",     MajorVersion in (22, 24, 26), "Supported - Apply November 11 security update",     MajorVersion == 27, "Alpha - Review unsupported production deployment", "Review manually") 
| extend Priority = case( SupportStatus == "End of Life", 1, MajorVersion == 27, 2,     MajorVersion in (22, 24, 26), 3, 4) 
| project DeviceName, SoftwareVendor, SoftwareName, SoftwareVersion, MajorVersion, SupportStatus, PatchReadiness, Priority
```

## Worth knowing

Also missed by last week's issue and worth reading if you argue about patch prioritisation: Microsoft Security Research looked at roughly 383,000 CVEs disclosed between 1999 and September 2026 and found about 2,056 of them, around half of one percent, linked to real-world exploitation. The exploited set skews hard toward system takeover — server-side remote code execution rises from 20 percent of published CVEs to 37 percent of exploited ones, local privilege escalation from 11 to 18 percent, client-side remote code execution from 4 to 13 percent, while cross-site scripting falls from 15 to 4 percent and denial of service from 16 to 7 percent. Takeover classes together account for 78 percent of exploited vulnerabilities, and operating system and system code rises from 23 percent of published CVEs to 41 percent of exploited ones. The uncomfortable half of the paper is the clock: the median vulnerability is patched in about two weeks on Windows workstations, over a month on Windows Servers, more than ten weeks on Linux servers and over a year on network appliances, while the mean time to a CISA KEV listing has fallen from 89 days for 2024 CVEs to 20 days for 2026 CVEs, with a three-day median. ([What exploited vulnerabilities have in common: A data-driven analysis of real-world attacks](https://www.microsoft.com/en-us/security/blog/2026/11/02/exploited-vulnerabilities-common-data-driven-analysis-real-world-attacks/))
